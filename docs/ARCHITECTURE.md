# Architecture Guidelines

## Default feature-first layout

```text
lib/
  main.dart
  app.dart
  core/
    config/ errors/ logging/ routing/ theme/
  features/<feature>/
    application/  # State controllers and feature orchestration
    data/         # Repository implementations and data adapters
    domain/       # Models and business rules, only when justified
    presentation/
  l10n/
    arb/
    generated/    # Generated by flutter gen-l10n; do not hand-edit
```

## Dependency direction

- Presentation depends on feature contracts/controllers, not concrete storage or HTTP clients.
- Data adapters implement repository contracts.
- Core must not depend on app features.
- Features must not reach into another feature's private implementation.
- Avoid circular dependencies.

## State and dependency construction

- Use Riverpod 3 for shared/async feature state; keep ephemeral UI state in Flutter primitives.
- Define providers beside the feature that owns the state or repository contract.
- Use constructor injection for plain Dart classes and Riverpod providers as the composition root.
- Do not introduce a second state-management or service-locator framework without a new ADR.

## Navigation and UI

- Use go_router from `lib/core/routing/`; keep route definitions centralized and URL-safe.
- Keep Material 3 ColorScheme/TextTheme authoritative. Add small shared spacing, radius and motion tokens under `lib/core/theme/`.
- Use Flutter `gen_l10n` and ARB resources for user-visible strings.
- Model loading, success, empty and failure states explicitly. Present safe messages and keep diagnostic details out of UI.

## Errors and diagnostics

- Map expected boundary failures to typed `AppError` values where useful.
- Use the injectable local `AppLogger` for diagnostics and Flutter framework/platform error hooks.
- Remote crash reporting is opt-in and requires a separate provider/privacy decision.
- Never log credentials, tokens, personal data or full request/response payloads.
